What to fix first

  1. Allocate MathLive only for active editing. Keep inactive equations as lightweight previews, with source and selection bookmarks preserved. The current queue eventually creates all 422 fields, including those outside the viewport, and retains them when Visual is hidden. The 8 ms budget is checked after a mount, so it cannot bound a single expensive connection.
  2. Remove repeated forced style and layout work. MathLive reads computed style immediately after insertion. Trace the style invalidations and the specific selectors; batch reads and writes, cache stable measurements, and reduce the number of interactive roots. The present traces identify the connection path, not one proven bad CSS selector.
  3. Stop full document replacement during ordinary typing. The production typing trace recorded six expensive projection installations, totaling about 5.84 seconds, with calls up to 1.37 seconds. Audit local-save acknowledgements and the source/preamble reconciliation effects before calling setContent and rebuilding EditorState. Keep genuine outside edits recoverable. Then stabilize document, macro, and completion-context props and avoid rebuilding unaffected node-view trees after each character. Source assembly and save planning themselves are small; scheduling publication alone does not stop replacement or DOM work.
  4. Make pagination incremental. Measure dirty blocks and visible neighbors, cache unchanged line geometry, and cancel obsolete pagination work. Avoid a whole-document measurement after each field mount or small text update. Retain page and selection correctness.
  5. Audit teardown and retained views. Check MathLive roots, listeners, timers, ResizeObservers, node-view portals, and detached DOM after close/reopen. Distinguish intentional hidden-view retention from a leak; one rising memory run does not prove a leak. Release or suspend expensive inactive resources while preserving drafts, selection, and undo.
  6. Separate loading feedback from editing readiness. Development module transformation/loading contributes a large cold-client wait. Keep the normal graph warmup or evaluate bundled development separately. Show useful paper previews early and admit interactive work after first paint; show cancellable progress for expensive loading and compilation.

Proposed acceptance targets: next-paint input latency below 100 ms at p95, no repeated editor tasks over 50 ms during ordinary typing or scrolling, bounded live interactive math editors, and memory that settles after repeated close/reopen cycles. These are targets, not results achieved by this task. Qualify them on the native candidate with the same manuscript and source revision after each repair.

Method and limits

  • CPU sampling at 1 ms; Chrome main-thread tracing including style/layout and V8 GC; Long Tasks API; animation-frame gaps; 100 ms heartbeat lag; live math-field connection/disconnection counts; CDP heap/DOM/task metrics; Windows process working set and CPU counters.
  • The typing sequence inserts “ Responsiveness capture.” at 60 ms nominal intervals, then undoes once; scrolling sends eight 500-pixel wheel events. View switches cover Source, Visual, and PDF, followed by close/reopen and cached page reload. Typing and autosaving affect only the copied project. A single undo may leave earlier text when slow typing splits undo groups; the copy is restored from verified originals between build runs.
  • Input latency is keydown to a subsequent animation frame plus task, a next-paint proxy, not exact OS-to-display latency. Automation and tracing can alter timing. Lighter controls omit CPU sampling and tracing but retain observers and timing wrappers. Each is a single sequence, not a statistical benchmark across many trials.
  • “Cold” uses a new browser context and cleared HTTP cache. OS file cache is not cleared. The first development capture includes substantial unbundled module transformation/discovery; the repeat uses the already prepared server graph. Normal Vite startup warmup is disabled for this diagnostic. Cached reload preserves browser cache but recreates the client; view switches reuse the already mounted Visual editor.
  • A remembered Visual mode can mount fields before the Source checkpoint; the initial production Source checkpoint records this. Read the field counts and whole document-opening interval rather than treating that checkpoint as a pure Source-only benchmark. Lighter controls explicitly request Source first.
  • The renderer source was frozen from a dirty working tree so development and production use the same product snapshot. Later concurrent product edits are not included in this baseline. Production was built in a separate process with NODE_ENV=production; source-map inspection confirms no React development runtime sources. No build or heavy analysis ran alongside accepted interaction captures.
  • The diagnostic client uses an empty conversation and separate profile, not the user's live chat history. The copy is inside the development checkout, so project metadata/background work differs from the original project location. Native Electron shell, live conversation history, and the original client/transport completion delay remain unqualified.
  • Windows 11, Intel Core i7-10510U, 8 logical CPUs, about 16 GB RAM; Chromium version is included in raw capture metadata. Other user applications remained running. This is not an isolated machine or a native process-level reproduction.
  • Failed pairing/cache/configuration attempts and the mislabeled bundle containing development React are excluded. Raw local setup files remain separate. No test suite was run, and no optimization was implemented in product code.
