# CI flake register

A test that failed CI on content that also passed it, with no fix merged yet.

## Quarantine

A failure that exactly matches an open quarantine row does not fail the required
`Check`. It does not remove a pull request from the merge queue, and it does not
fail main's required check. The rule is in
[AGENTS.md](../../AGENTS.md#git-upstream-and-delivery).

- **Exact match.** A match needs the job, the failed step, the test id and the
  failure signature. `Check` reads each failed job's log. A job passes only when
  every failed test, failed suite and unhandled error in it matches an open row, and
  vitest's own counts agree. A failure it cannot read blocks.
- **Still visible.** The test still runs, and its job stays red. `Check`'s summary
  lists each quarantined failure with its row.
- **Expiry.** A row has an owner and expires 7 days after it was quarantined. From
  the day after expiry it blocks again, unless the cause is fixed (the fix removes
  the row) or the owner extends it.
- **No matching row.** These failures block as before. So does a cancelled job, a
  job that failed outside its row's step, and anything in setup, build, typecheck,
  format/lint, documentation or provenance. Those are never quarantinable.
- **Read from the base branch.** `Check` reads the rows from the base branch
  (main, or the queue's base), never from the tested change. So a change cannot
  quarantine its own failure: add a row in its own pull request first.
- **Releases.** Releases still need a CI run with no failed job, so a quarantined
  failure needs a clean rerun before that commit ships.

The machine-readable rows are in
[`.github/scripts/ci-quarantine.json`](../../.github/scripts/ci-quarantine.json),
and the matching is in `ci-quarantine.cjs` beside it. Each row's id and expiry
must also appear in the table below (a Node test checks this).

Each new signature gets an owner and an investigation on the day it first
appears. The daily CI care task adds every occurrence of a row to its line below:
date, run link and running count. Rows that are near expiry or frequent go first
for a fix.

## Fixed

`tunnel.test.ts` › SSH launch during desktop update › waits for a boot service between two
servers (archive: true) failed six times from 2026-11-18 to 11-19 with `launcher failed: Error:
spawnSync /bin/sh ETIMEDOUT`: scheduled main run
[44288104242](https://github.com/ScientFactory/scient-desktop/actions/runs/44288104242), queue run
[44261127219](https://github.com/ScientFactory/scient-desktop/actions/runs/44261127219) and PR runs 44258177112, 44273669908,
44359842716 and 44446249810. The archive launcher starts the real SSH helper on every
one-second poll, and each start loads about 640 modules, most of them `@t3tools/contracts`
(246 files in Scient, 111 in T3). The test's five-second wait meant seven starts, which took
18–22 s of the harness's 30 s `spawnSync` on passing CI runs. Ten copies at once on macOS
efficiency cores (`taskpolicy -c background`) failed 10/10 the CI way; the archive case now
waits one poll (three starts) and passes 10/10 in 18–19 s under that load. The host-Node case,
whose polls are cheap, still waits across five. Owner: Remote environments.

`imageNodeView.browser.test.ts` › Markdown image NodeView › keeps the old image while
replacement uploads and follows movement before completing failed on 11-18 (PR run
44284760346, Web 9) with `complete is not a function`: the upload never started. The test
clicked the real file input; headless Chromium dismissed the native chooser with a `cancel`
event, which cleared the pending replacement before the test's `change`. The test now stubs
the input's click. At `SCIENT_TEST_CPU_THROTTLE=6` the case alone failed 4/4 before and passes
4/4 after.

`ClaudeAdapterV2.test.ts` › ends a subagent's SendMessage with its result when the CLI exits
while the resume waits failed twice on 11-17 with `Claude captured Stop close remains
unresolved.` (row `claude-captured-stop-close`). The fault was in the test. Exit cleanup
holds the next start until it has read subagent transcripts from disk, and the test waited a
fixed 2,000 scheduler turns for that real I/O. It now waits for the first query's worker,
which ends only after that cleanup, before it starts the next turn. With 300 ms added to
that cleanup, the old wait fails with the CI signature and the new one passes.

Windows packaging's "Installed desktop must survive the smoke interval and drain on
shutdown" failed from 2026-11-09 to 11-11. The fault was in the check, not the
app. A helper the backend started (Azure CLI's Python, from source control
discovery) inherited the app's output pipes and could hold them past the 8 s drain
after a forced stop. The smoke now captures output to files and requires the
app's own processes to end. It also checks a normal quit.

Claude process cleanup's "stops the CLI's detached descendants when the server
goes away" failed in
[queue run 43942817923](https://github.com/ScientFactory/scient-desktop/actions/runs/43942817923/job/133565081200)
on 2026-11-16 with `the CLI stopped too: expected true to be false`. The adapter
and test were unchanged from the green PR head. The test awaited the
descendant's exit, then assumed the CLI had already exited too, but those
process exits have no ordering guarantee. The correction awaits both within the
existing 5 s budget, without changing runtime cleanup. Owner: orchestration
lifecycle.

Sources list's "keeps the project backend in the shared scroll area with every row
mounted" timed out at 30 s three times from 2026-11-17 to 11-18 (queue run
