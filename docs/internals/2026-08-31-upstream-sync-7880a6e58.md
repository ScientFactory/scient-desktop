## Generic files: corrected product assumption

The owner explicitly requested file attachments of all types, with no delay for
a mobile picker. The previous alignment's blanket
`SCIENT_GENERIC_FILE_ATTACHMENTS_ENABLED = false` was an implementation
assumption, not an approved product restriction. This alignment removes both
Scient gate modules and restores the upstream capability, normalizer, and
desktop/web entry points together.

There is no extension or document-type allowlist. PDFs, spreadsheets, archives,
audio, video, source code, unknown extensions, and extensionless files can use
the generic path. SVG and TIFF use that path when they cannot use native image
input. HEIC/HEIF conversion remains intact. Empty, unreadable, oversized, or
failed uploads remain rejected with an actionable state. File acceptance never
means automatic execution or guaranteed native understanding by every AI.

Compatibility was checked at the actual consumers:

- The server validates completed-upload claims and confined asset storage;
  generic files do not bypass those boundaries.
- Provider delivery uses native attachment input where supported, otherwise the
  existing server-local file path and provider tools. No new provider protocol
  or login behavior is introduced.
- Web/desktop retain generic files in drafts and prompt stashes. Captioned
  image paste remains an attachment; ordinary rich-text clipboard data is not
  mistaken for a generic file.
- Completed-response forks copy retained files as well as images. Rekeyed file
  IDs retain the extension expected by asset lookup; a regression test proves
  the copy remains readable after the original is deleted.
- Current mobile renders non-image attachments with a named, signed-asset
  **Open file** action and retry/error states. A mobile generic-file picker is
  not required for desktop/web acceptance. Future unknown attachment kinds
  receive a truthful unsupported label instead of being dropped.
- Generic-file queueing and restoring a sent user message into an editable
  fork draft are not implemented in this checkpoint. Those actions fail
  explicitly without silently omitting files; ordinary send/steer and
  completed-response forks retain their existing paths.
- This does not claim old released clients acquire a new file UI. Their
  compatible decoding remains distinct from presentation: an older mobile
  renderer may omit generic attachment controls. Updated clients are required
  for the new attachment experience; this is not identical old-client UI parity.

The maintained alignment protocol now distinguishes safe shared-contract
handling from identical client UI, and approved product policy from an earlier
agent's assumption. User documentation describes the actual support and limits.
