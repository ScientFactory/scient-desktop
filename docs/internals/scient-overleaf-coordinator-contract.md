## 1. Basis and dependency

Preserve manual, folder-first manuscript synchronization: private bare repository, explicit base, immutable review, local application, verification, then one non-force push. Editor saves, builds, opening a document, and background polling never initiate Cloud sync.

## 2. Authority and invariants

1. One active manual connection owns a canonical manuscript folder in one physical checkout and server environment. Refuse equal, nested, overlapping, or alias-equivalent folder registrations within that environment. Repository identity or project ID alone cannot authorize another worktree.
2. Every operation starts with authenticated environment scope, current workspace binding and canonical folder resolution. Recheck before local mutation and before sending. Changed root/folder device/inode, generation, scope revision or revoked authority invalidates the operation. Missing reliable physical evidence fails writable admission for the initial macOS delivery.
3. The server constructs trees, plans, IDs, retention locations and Git destinations. Requests cannot supply arbitrary tree/commit IDs, apply journals, storage paths or credentials embedded in URLs. Cloud v1 accepts normalized credential-free official project URLs; additional hosts require a separately reviewed host policy, not a free-form Git endpoint.
4. A plan is immutable. Confirmation names its ID and digest plus the current connection revision; it cannot inject different choices, selected files or bytes. Changing choices requests a replacement plan and invalidates the previous one.
5. Local application precedes publication. Skips, interrupted units, unresolved Scient conflict material, changed retained copies or failed publication verification stop outgoing publication. Preserve the applier's per-identity base rules; never reconstruct a partially advanced base by path alone.
6. Pin and durably record a publication attempt before invoking push. Only positive evidence establishes acceptance. Absence of evidence, unavailable history and command failures do not establish rejection.
7. Recovery never sends. A new publication requires a current explicit review and confirmation, even after rejection or restart. No force push, background retry, automatic commit splitting, or retry on a request transport timeout.
8. Save locks and the new checkout barrier cover participating Scient operations. Arbitrary shell writers, external Git commands, other server profiles and late open handles are outside that exclusion; retained bytes and attention handling remain necessary. Do not promise a globally atomic snapshot of a folder with such writers.

## 3. State, admission and persistence

Separate connection facts, an ephemeral review, a running command, and durable recovery evidence. Do not persist a long-lived worker waiting for the user to approve a review.

The connection document contains its schema/revision; binding and physical identities; normalized host/project/branch; `mode: manual`; current base and base generation; references to twenty prior bases and ten local snapshots; managed/local-only paths; recorded conflict/attention paths; retention manifest; and an optional active apply/publication record. Tokens stay in `ServerSecretStore`, under a server-derived key for the exact host. Secret renewal is serialized against token use and advances a host credential epoch, invalidating ephemeral plans without erasing the base. It must not acquire multiple connection locks while holding the credential lock; operations check that epoch when using a credential.

The running command has a server-generated operation ID, authenticated initiating session, client request ID, phase, cancellation handle and receipt. Admission is non-queuing: a competing command receives `operation_active`; it cannot cancel or release the owner's lock. Same request ID and identical payload returns the same operation/receipt; reuse with a different payload fails. Persist a bounded receipt for confirms and destructive management actions so a lost HTTP response cannot execute the action twice. A duplicate confirmed request returns status/recovery, never another push.

Receipt cleanup may remove resolved terminal history, but cannot release active/unknown evidence or revive a consumed review. A repeated ID whose receipt has expired returns an expired/not-found result; it cannot reconstruct and execute the old confirmation. A restarted service has no valid ephemeral reviews to replay.

Use one feature-wide connection-registration mutex and one non-queuing operation reservation per connection. A short connection-state mutex protects compare-and-set transitions; the reservation preserves command ownership when that mutex is released to wait for a checkout section. Status reads and a rejected request cannot release the reservation. Preserve the existing single applier instance initially; its semaphore serializes local applications across connections. This is a throughput limit, not cross-process protection. Keep reviews outside those locks.

Writable admission requires a process-held exclusive lease for `stateDir/overleaf`. Use a dedicated SQLite lease file/connection (the server's existing `node:sqlite` client), separate from `statev2.sqlite`. Try to acquire it at each writable admission until held, then keep it for the service lifetime; while another process holds it, admission returns a typed `state_locked` refusal. Acquiring lazily, rather than once at startup, keeps an overlapping restart from disabling the feature for the new process's lifetime. Do not steal a lease on a timer or use PID existence alone; the existing `proper-lockfile` session-lock pattern is stale-mtime based and is deliberately not reused here. Kernel release after process death permits recovery, not replay. Implement and qualify this lease in PR B; it is not an existing server-wide guarantee. Independent profiles remain separate environments, not one machine-wide lock on arbitrary writers.

Metadata lives in a private `stateDir/overleaf` tree; the bare repository stays outside the workspace repository. Write each connection replacement to a same-directory temporary file, sync it, rename it, then sync the directory. Git refs and JSON are not one transaction: create immutable intent/object refs first, then publish the connection reference. Unreferenced artifacts are harmless orphans; a referenced missing/corrupt intent is a blocking error. Never clear the only pointer to recoverable work before its final base/attention transition is durable.

Reviews expire after 15 minutes, are limited to one current plan per connection, and do not survive a server restart. Apply intent and publication records do survive. Durability here targets process interruption with fsynced records; do not claim power-loss safety for every filesystem/controller without separate qualification.

## 5. Plan validity and publication boundary

The plan digest binds connection/base revisions, checkout mutation epoch, host credential epoch, current authority tuple and folder identity, captured managed tree, fetched remote head/tree, approved additions/local-only decisions, grouped choices, candidate tree, recorded conflict paths, review warnings, and the required acknowledgements. The initiating renderer/session and its flush acknowledgement belong to the operation receipt; they do not grant filesystem authority.

Before confirm, PR C flushes the initiating renderer's manuscript sessions again. PR B then re-inventories and checks contents/absence, selected addition paths, identities and budgets. Metadata timestamps and a client “saved” boolean are insufficient. Flush failure stops the client flow. New unselected files are not quietly added; inventory changes that affect the review require a replacement plan. If an agent becomes active after preparation, refresh its warning/acknowledgement before applying.

Refetch immediately before local apply. Any remote head change, even equal-tree history change, invalidates this plan because its parent and recovery evidence changed. Return a new review; do not automatically accept the prior confirmation for different inputs. A later remote move is still possible and is handled by the non-force push result.

After apply, independently capture and hash the exact publication domain again; do not infer it from the applier's outcome. Include all remote/managed entries, approved additions, and explicit deletions. Preserve fetched remote files; a file rejected by inventory is an error, not permission to omit it from the outgoing full-project tree. Exclude only durable local-only and host staging material. If a remote entry collides with a local-only or unchecked local file, require an explicit reviewed collision resolution that captures/preserves the local bytes; never treat exclusion as local absence or silently overwrite it. LFS/unsafe/oversized remote content refuses the operation before mutation. Existing alias-only rename and portability refusals remain typed preflight errors; the coordinator does not invent a workaround.

Require that captured bytes/absence match the confirmed candidate, with no interrupted units or recorded unresolved markers. Pin the exact blobs/tree, build a commit whose single parent is the plan's fetched remote commit, and record its identity. Do not reread mutable workspace files to construct push contents after this verification. Edits after verification belong to a later sync and cannot alter the pinned candidate. Return accepted publication of that candidate separately from whether the latest disk content is still synchronized; recapture/invalidate status before claiming “up to date.”

This is byte verification of the participating files, not an atomic whole-folder transaction against arbitrary external writers. Normal Scient writes retain revision checks and the shared per-file locks. File instability during capture fails/replans; it is not solved with a fixed delay.

## 6. Apply and publication recovery

### Local application

Durably reference the apply ID, intent kind (`sync-apply` or `retained-restore`), plan digest, connection/base generation, canonical folder identity and retention location before calling `WorkspaceApplier.apply`. The applier writes its own hash-bound `plan.json` and progress record before displacement. Recovery calls the same apply ID without supplying a new plan, using the current host helper configuration. A retained restore uses a revision-checked, reviewed single-file plan and adopts its attention/retention results without adopting the applier's computed merge base. An exchange journal cannot become fallback after an update.

After a crash between applier completion and connection finalization, reconcile the recorded result once and persist the returned per-identity base/attention before clearing the active apply link. Do not advance base twice. Interrupted groups remain forced conflicts until a reviewed resolution; stale capture with no mutation yields replan. Primitive journal identity, rather than content equality or the outer done-mark alone, determines owned work. Retained-copy changes and remaining structural staging block publication.

Startup scans bounded metadata and exposes recovery-required without Cloud traffic or fresh publication. Before a new connection operation, recover only under verified registration and admission. A checkout restore/removal must settle or refuse pending local recovery first; it cannot bypass journals merely because the original process died.

### Publication

The durable attempt records a monotonic attempt number, operation/request/plan identities, parent remote commit, candidate commit and full tree, post-apply base generation, authority tuple, branch, and `outcome: unknown` before the send boundary. Pin candidate and parent refs first. If the record cannot be synced, no push is allowed. A crash immediately afterward is conservatively uncertain, even if Git was never invoked.

| Evidence                                                                                                                                        | Base and next action                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Explicit accepted response, or a fetched current head/whole tree equal to the candidate                                                         | Persist candidate as base and record the acceptance evidence in the same connection replacement. Later disk edits remain local changes.                                                                       |
| Candidate commit reachable from fetched head, or exact candidate whole tree in bounded history after its recorded parent                        | Adopt candidate as base; prepare current remote changes against that base. An accepted-then-reverted change becomes incoming. Equality proves content convergence, not attribution to a particular publisher. |
| Explicit out-of-date result from this push                                                                                                      | Record rejection; preserve the post-apply base. New fetch/plan/review is required.                                                                                                                            |
| Send admission refused after the attempt was recorded (checkout epoch changed, connection suspended)                                            | Record `not-sent` with `send-refused` evidence; preserve the post-apply base. Certain, because Git was never invoked; a crash before that record leaves `unknown`.                                            |
| Missing/rewritten/truncated history, unavailable parent, no positive match, offline/auth failure, cancellation, timeout, unrecognized rejection | Keep unknown; preserve base and the attempt. Never infer “not sent” from absent history or unchanged current remote.                                                                                          |

Reuse the repository's positive rules; production recovery belongs in the coordinator/service, not in the interactive probe CLI. Check current equality, then bounded first-parent history (64 entries initially), then reachability where available. Bound the work by executor time/output limits. Return evidence kind and whether history was incomplete; none of these reads is a retry.

For a still-unknown attempt, the next review prominently identifies the earlier candidate and possible duplicate/overwritten changes. A subsequent confirmed apply/publication requires explicit acknowledgement of that attempt and a freshly constructed current plan. If the later operation advances the base, archive the old attempt as **superseded but unresolved** atomically with that base transition, including for an incoming-only sync. A new outgoing operation records its own monotonic attempt before sending. Do not resend the old commit or treat supersession as proof of rejection. Recovery can advance a base only when the attempt remains authoritative for its recorded generation; late older evidence is informational and cannot rewind a base established by a later reviewed apply or accepted attempt. While that later local apply is pending, settle it before classifying any old attempt. Retain/pin unresolved evidence; when its storage budget is exhausted, refuse new work rather than drop it.

If the accepted/rejected finalization write fails, the already durable unknown record remains. Recovery classifies it later; the HTTP failure must not trigger a second send. A lost client response similarly returns the command receipt/recovery status on repeat, not another worker.

## 7. Base, identity and connection management

New connection starts from an explicit empty base and a visible first-sync/no-history warning. Capture existing local and fetched remote files before choosing their union/resolution. Publication only follows the reviewed choice.

Renewing credentials, reconnecting the same active connection, restarting, or trusted relinking the same project preserves its known base. Directory spelling, repository remote, or copied project ID alone is insufficient physical continuity. A revoked/replaced root needs explicit relink, not implicit adoption.

Unreadable metadata or inconsistent/missing base refs blocks automatic recovery. Preserve/quarantine the originals and report what is unavailable. An explicit reviewed history reset may establish a new empty base only when no unowned local intent/staging remains; it never destroys unknown publication or retained evidence. Lost history is not silently equivalent to a new empty project, and a damaged connection cannot publish until that acknowledgement/review is complete.

Disconnect archives state and retention; reconnect to that archive uses the same verified history or explicitly reviews its loss. A separate explicit purge action can be a later feature. PR B does not purge unresolved retention on disconnect.

## 8. Retention, disk failures and inventory budgets

Select storage on the server: `stateDir/overleaf/retained/<connection>` is the applier's application directory. Require it to be on the manuscript checkout's device, outside the checkout (so checkpoint `git clean` and worktree removal cannot reach it), a verified non-symlink directory owned by the server user with private permissions, and record its identity in the connection. If the checkout is on another volume, refuse writable admission with `cross-volume` (owner decision 1). Do not create a vault beside the checkout, fall back to `.scient` inside a checkout, accept a client path, or copy across volumes.

The vault survives checkpoint `git clean` and target worktree removal. Its receipt is discoverable from the connection archive. The applier's in-folder structural source copies remain separately recorded; exclude those exact paths and reserved staging patterns from capture. Never garbage-collect staging while its unit is unresolved.

Recheck displaced copies at apply completion and each explicit sync/recovery. Keep each releasable copy for at least seven days **and** through completion of a subsequent sync. Changed, ambiguous, interrupted, or explicitly retained copies are never automatically deleted. No finite retention period can guarantee detection of an indefinitely held external handle; state that limit. PR B supplies bounded list/compare and revision-checked restore results; PR C presents them. Cleanup is local, serialized, and cannot advance a base or send network traffic.

Preflight free space for intended bytes, worst-case displaced copies, synced intent/progress records, and required Git objects; reserve working headroom where the filesystem supports it. Free-space checks are advisory, so inject disk-full at every later write too. A failure before durable intent yields no mutation/send. A failure after displacement keeps all journals/copies and reports recovery-required; if finalization fails, it must not claim completion or release evidence. A disk-full push interruption remains unknown.

Preserve revision-5 inventory rules: managed paths plus explicitly selected additions; no `.gitignore` interpretation; exclude repositories, links, reserved paths, LFS pointers, droppings and application storage. Build leftovers/hidden additions are visible but unchecked. Do not read/hash unchecked additions except a bounded prefix needed to identify a forbidden file format. Enforce limits on the fetched tree as well as local files before materialization.

## 9. Checkout barrier and lock order

Introduce a server-owned barrier keyed by canonical physical checkout identity, shared with V2 checkpoint restoration and participating VCS/worktree paths. It is a new integration service, not the checkpoint service's existing keyed lock.

Two operations are mutually exclusive: an Overleaf application section and a bulk checkout mutation section. A bulk request closes new apply admission immediately, waits for a running applier to settle, then mutates. It increments a checkout epoch and invalidates plans, even on partial failure. It does not reset the Overleaf base: the resulting checkpoint/branch content must be reviewed as local changes, including the historical-revert warning.

Hold the Overleaf application section through adoption of the applier's durable result. Release it before potentially long network publication. After verification and durable attempt recording, publication uses a short barrier guard to check the epoch and admit this owner/attempt exactly once for sending; an already suspended or changed checkout refuses admission and records the attempt `not-sent` (owner decision 2); a crash before that record leaves it `unknown`. This atomic host send-admission is the ordering boundary, not a claim of atomicity with the remote server. Mutations afterward are later local changes, even if packet delivery occurs afterward too; they do not alter the pinned candidate or trigger a retry. Do not hold the checkout section while awaiting a network response. A pending local journal or unresolved structural staging makes bulk mutation fail with attention rather than allow `git clean` to erase recovery evidence. Worktree removal preserves the outside vault and marks its connection unavailable.

Do not hold the connection-state mutex while waiting for the checkout section. Retain the command's operation reservation, acquire the checkout section, then the state mutex; recheck plan/base/epoch after acquiring both. Complete remote refetch and other network prerequisites outside the application section; after waiting for it, revalidate local capture/authority and refuse if the checkout epoch changed. The collaborator can still move the remote after a fetch; non-force push handles that race. If prepare discovers a pending apply after admission, release its state mutex before taking the recovery section. Bulk code that discovers a pending local apply recovers it inline when that connection's operation reservation is free (owner decision 3, below); if the reservation is held, or inline recovery fails, it returns recovery-required and releases its section. It never waits for a recovery command while excluding that command, nor on a reserved worker that itself awaits the section. Resource release occurs in finalizers; nested callers share one barrier token rather than reacquiring it. Ordinary per-file save locks remain the innermost locks. Tests must demonstrate no deadlock between confirm, recover, checkpoint, cancellation and removal.

Wire `CheckpointService.restore`, `GitWorkflowService.switchRef`/pull/target removal and relevant delegated mutations. Audit startup auto-pull's direct VCS call, VCS broadcaster, thread/worktree launch cleanup and lower-level bypasses; cover actual filesystem mutation, not merely HTTP entry points. Creating a different worktree does not suspend the connected checkout unless its implementation actually mutates it. Do not claim control over agent shell Git commands.

A checkpoint restore or other bulk mutation that finds a pending local apply for a connection on its checkout recovers it inline, under the section it already holds, when no Overleaf command holds that connection's operation reservation (owner decision 3). It refuses only if that recovery fails or the connection is busy; recovery is local-only and never sends.

## 10. Editor and activity boundary

PR B exposes a typed prepare/confirm contract whose flush acknowledgement includes environment, renderer/session, manuscript scope and completion. The server still verifies disk bytes independently. It is a warning, not a shell-write lock; late writers still use retained-copy protection.
