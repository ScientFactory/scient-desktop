## Composition

### Event pruning (#29806)

T3 replaces event compaction with pruning. A background pass runs a minute after startup and then
every 6 hours. It deletes events older than a day that the projections already cover. The
deletion cannot be undone, and `verify` and `rebuild` now exist only in the test kit
(`testkit/ProjectionReplay.ts`). Three Scient readers needed events that pruning deletes:

- **Legacy handoff bodies.** Handoffs saved before `historySource` existed kept only an event
  reference. Such a handoff became unreadable once its event was gone. Three changes fix this:
  - `recordContextHistory` now always stores a copy of the body.
  - The Scient-track migration 28 (`CopyLegacyHandoffSources`) fills the copy for existing rows.
  - A test prunes the event and still reads the summary and history.
- **Workspace authority revision.** The thread stamp read the previous thread state from the event
  log. After pruning, a thread that had moved worktree would get a new revision on every metadata
  update, which would wrongly invalidate Overleaf review, Compute and forks. The stamp now reads
  the prior state from the thread projection. Only states appended in the same batch come from the
  log, and pruning never reaches those. The new pruning test fails on the old stamp.
- **V1 import baselines.** Source reconciliation compares V2 edits against the original
  `migration:v1:*` import event. The importers also use those events as "already imported"
  markers. One Scient keep-rule, `scient-fork/EventPruneRetention.ts` (one marked line in the
  prune SQL), keeps them. V1-imported history therefore stays unpruned, as it was before this
  alignment.

Scient's two `rebuild` edits move into the test kit:

- the handoff capture-order reset;
- filling `turn_item_positions` after replay.

About 20 Scient tests use T3's `ProjectionReplay`. `ws.ts` takes T3's `prunedThroughSequence`
snapshot fallback for old cursors.

Two other readers degrade safely and are unchanged:

- `AttachmentPublicationProof` keeps an attachment pinned once its evidence is pruned.
- `LegacyQueueCutover` keeps a claim once its evidence is pruned.

### Shareable thread links (#26290, #29815)

T3's Copy thread copies `https://app.t3.codes/threads/…`. Scient has no hosted origin yet, so
that link would open T3. The owner wants shareable links in the next PR, so:

- **The seam.** T3's hosted-link machinery is kept behind one Scient seam,
  `packages/shared/src/scientThreadLinks.ts`. Its `scientHostedThreadOrigin()` returns nothing
  today.
- **What Copy thread copies today.** Copy thread, chip copies and the thread action menu copy
  Scient's in-app link, as before.
- **Outside MCP clients.** They get `<origin they reached>/threads/<env>/<thread>`, which T3's new
  web route opens.
- **Pasting.** A pasted `app.t3.codes` thread link still becomes a chip.
- **Phone-app link files.** `.well-known/*` and `apps/web/vercel.ts` stay as T3 ships them. They
  only take effect on T3's domain, and removing them would conflict on every T3 change.
- **Follow-up.** The follow-up sets the origin, teaches the parser that origin, and swaps in
  Scient's app IDs.

### Forks after an undo (#29902)

T3 drops turns of rolled-back runs from a live native fork. Scient's frozen fork path adds the
source's later live turns, so it now applies the same rule. The rule lives in one helper,
`providerTurnsOutsideRolledBackRuns`, which T3's path also calls. A unit test covers an undo that
happens after the fork was frozen.

### Subagent questions reach a busy parent (#29909)

Question notices now steer into a running parent turn. Scient's `steerExecutionThread` ran a
notice under the composer's current modes. A mode change while the parent ran would therefore
restart that turn, which T3 never does for a notice. Notices now keep the run's modes. Scient's
queue holds, Droid's no-steer rule and the effect-worker retry all compose.

### Managed policy

- **Group Policy templates (#29862).** `scient policy` writes `scient.admx`, `scient.adml` and
  `scient.mobileconfig`. They use the namespace `ScientFactory.Policies.Scient`, the registry key
  `SOFTWARE\Policies\ScientFactory\Scient` and the macOS domain `com.scientfactory.scient`. All of
  these come from the same constants the reader uses. A test proves the match and that no T3 text
  remains.
- **Providers (#29915).** T3's test that a policy can name every built-in provider failed for
  Droid, Oh My Pi and Scient Agent. They now fall under the policy like every other provider.
- **Update mirror (#29911).** Scient installs its server from npm, not from T3's single-file
  archives, so no archive code returns. With a policy `feedUrl`:
  - `scient update` reads the version from the mirror's feed file, including Beta's
    `beta*.yml`;
  - updates started from another device install `<feedUrl>/v<version>/scient-server-<version>.tgz`.

  T3's refusals of preview builds and wrong-track feeds are kept. The user guide says which update
  paths follow the mirror.

- **Startup recovery (#30319).** The stop message says Scient and links to Scient's releases.

### Pi (#30187)

Every short-lived Pi launch now runs `--offline`, so a stop mid-refresh can't spend Pi's
single-use OAuth refresh token. That covers T3's launches and Scient's own discovery, status and
text-generation launches, the latter through one `shortLived` launch policy. Scient's stdin fix for
the stop order stays until T3 merges #30025.
