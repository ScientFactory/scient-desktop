## 2 Obtain the platform decision before activation work

Prepare a bounded feasibility/options brief. Linux lacks the strict current-root authority required by the service; Windows lacks implemented exchange/complete creation and shared coordination. Compiler discovery alone cannot close these contracts. Yaacov chooses the release strategy.

- **Positive Linux and Windows support:** implement and qualify the missing primitives, with changed save/create/rename, competing writers, unknown outcome/restart/replay, volume/permissions and consumer recovery. Linux's root-object versus current-path authority mismatch requires a design/proof decision; do not relabel the capability or weaken admission.
- **macOS-first activation, existing publisher elsewhere:** select the backend before namespace work, with one service owner and explicit capabilities. Preserve established Source/PDF behavior elsewhere and scope new Visual guarantees to qualified hosts. Never fall back after an uncertain or retained macOS operation. Both modes need coherent retries, currentness, upgrade and consumer handling; clients must not infer exact durable receipts from a backend that does not provide them.

Rough planning ranges, assuming experienced ownership and target-host access: **1–2 engineering days** for feasibility; **3–7 engineering days** for macOS-first routing and its consumer/qualification closure; **2–4 engineering weeks** for positive Linux/Windows support, with high uncertainty and possible longer work if authority semantics require redesign. These are judgement-based estimates from missing mechanisms, not measured forecasts. They exclude remaining Visual recovery repairs, unrelated CI fixes, review and release acceptance. Firm them up before committing to a schedule.

Activate the chosen publication backend and its required client recovery contract in one coherent PR. Include stable intent identity, supported outcomes, pending-work preservation and actionable retained/unknown review. History conveniences can follow. MacOS-first is the likely faster candidate, not an automatic choice or an integrity waiver.

## 3 Close recovery and rename ownership before Visual enablement

Make R1–R7, SP2–SP4 and SP8 a dedicated work package. SP5 informs pending-input ownership; SP1/U3 cover upgrades. Several IDs overlap and are not independent defect counts.

Route ordinary TeX rename through every actual owner, including IME/math and the reference form on its `.bib` target. Hold source/destination recovery identities coherently. Preserve foreign/unresolved records through migration and failed cleanup.

A v1 single-writer guard is an option only if it proves:

- One resolved file owner across supported panes/windows/connections; aliases and rename source/destination cannot bypass it.
- Every source, field, parked-recovery, restore/discard and delayed/background writer obeys the same fenced owner generation. Disabling another editor's input is insufficient.
- Save/rename settle or refuse every actual pending participant, including `.bib` forms and multiple views in one window.
- Ownership survives supported saves/renames. Crash/reconnect cannot transfer it merely by timeout while losing the prior owner's sole work.
- Maintained two-contender, stale-callback, foreign-record, exit/restart, old-checkpoint and explicit-recovery cases preserve all owned work.

The parked array is per-document (`parkedKey(key)`), not one global array. Complete file exclusivity could contain that same-key race. It does not repair R6/R7/SP4/SP8 or same-window preflight. Compare atomic storage with this guard's complete cost; a guard is acceptable only with proof the unsafe paths are unreachable and the residual correctness repairs land.
